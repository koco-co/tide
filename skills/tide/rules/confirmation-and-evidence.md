# 确认门与证据规则

## 三道确认门

1. 分析确认：展示脱敏接口摘要、拟覆盖场景、排除项和未知项。确认前不生成测试代码。
2. 写入确认：展示精确相对路径、完整内容或可审查差异及回滚范围。确认前不写入项目。
3. 执行确认：展示精确 pytest 节点、已确认环境和目标。确认前不启动 pytest。

前一道确认只授权对应阶段，不能推定后一道确认。用户取消、拒绝或表达不明确时停在当前门前。

## 双轴状态

生成状态：

- `PASS`：确认清单中的测试全部生成、审查并写入。
- `PARTIAL`：只完成已确认范围的一部分，并准确列出缺失项。
- `FAIL`：没有形成可交付的生成结果，或写入事务失败且已回滚本次新建文件。

执行状态：

- `NOT_RUN`：用户未授权执行或明确选择不执行。
- `PASS`：确认的 pytest 节点实际返回成功。
- `FAIL`：pytest 已启动并返回失败。
- `BLOCKED`：环境、目标、文件完整性、运行时或确认条件不满足，pytest 未启动或被安全停止。

不得以生成成功代替执行成功，也不得以静态审查代替真实 pytest 结果。

## 证据范围

- `manifest.json` 记录运行编号、脱敏摘要散列、环境、必需运行时环境变量名、生成文件相对路径与内容散列，不记录变量值或源码正文。
- 执行计划摘要只绑定必需环境变量名及其当前存在性；不得对凭据值生成可持久化散列或其他离线校验材料。
- `report.md` 记录生成结果、文件清单和执行前状态。
- 执行后新建 `execution.json` 与 `execution-report.md`，记录精确节点、返回码、输出大小与散列；不持久化 pytest 原始输出。
- 报告中的每个“已验证”结论必须能追溯到实际命令、退出码或文件散列。
- 外部环境行为、业务副作用和未观察到的系统状态没有证据时标记未验证。
